# Change: 强化 readiness 探测并发与配置错误边界

## Why

当前 readiness 请求在应用状态锁内同步执行依赖探测；慢依赖会阻塞其他健康请求，多个并发请求还可能重复发起探测。配置加载器对非法整数、布尔值、未知字段、损坏行和不存在文件静默回退或忽略，生产启动无法可靠区分“使用默认值”和“配置错误”。

## What Changes

- 为配置加载增加可诊断的解析错误，非法类型、未知字段、错误层级、损坏行和文件读取失败均使启动校验失败。
- 保持 `loadConfig` 的现有调用形状，同时把加载错误纳入 `validateConfig` 和 startup 响应，避免业务模块各自处理配置异常。
- 将 readiness 探测从全局状态锁中移出，使用 single-flight 合并并发刷新请求，避免探测堆积。
- 并行执行实际启用的 MySQL、Redis 和 HTTP AI 探测，并使用一个统一的总 deadline，包含地址解析和连接阶段。
- 暴露最近探测时间、耗时、总次数、失败次数、恢复次数和进行中状态，为后续日志/指标模块保留稳定的观测边界。
- 增加基础测试、HTTP smoke 和运行文档，明确配置错误退出与依赖暂时不可用的区别。

## Non-Goals

- 不实现数据库健康 CRUD、schema migration 或依赖连接池重构。
- 不改变业务 API、认证模型、仓储协议或 `/health` 的兼容 HTTP 200 语义。
- 不在本 change 中实现 SIGTERM/SIGINT 优雅停机和端口绑定失败策略。
- 不将 MongoDB 纳入核心 readiness；当前仍保持可选能力边界。
